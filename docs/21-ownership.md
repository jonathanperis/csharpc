# 21 — Who owns what: the ownership map of the corelib

Issue [#191](https://github.com/jonathanperis/csharpc/issues/191), child of the policy issue #187. The owner's
principle: **csharpc owns the compiler (C#/IL to LLVM, the IL front-end, the driver, the toolchain), the C runtime
(GC, exception dispatch, threads, the OS boundary) and a thin contract layer** (the internal members of the few core
types whose layout is tied to our runtime: String, Array, Object, Type, Exception, Thread, RuntimeHelpers, Unsafe, the
span helpers). **Everything else is upstream's**, taken from the pinned .NET version's framework IL, including most of
System.Private.CoreLib. Only the code that is necessary stays.

> The tables below are the snapshot taken before the Regex flip (#206): the Regex shadow (the `Regex` rows) is deleted and
> `ownership.tsv` no longer lists it; the totals are regenerated by `tools/il-first/ownership.sh` on the next refresh.

This page is the map from today's `src/Csharpc/corelib` (354 files, 169,705 lines, 8.1 MB) to that principle. The
per-file data is [`tools/il-first/ownership.tsv`](../tools/il-first/ownership.tsv); regenerate it, or print the tables
below, with:

```bash
tools/il-first/ownership.sh             # rewrites ownership.tsv
tools/il-first/ownership.sh --summary   # the tables of this page, from the same data
tools/il-first/ownership.sh --contract  # the runtime entry points of the framework assemblies (below)
```

The ADR 0023 per-library table (the A/B runs of #187/#188/#189) links here for the "lines removed" column; nothing here
changes a default.

## How the map is made

- **What a file shadows.** Every `[Shadows("...")]` / `[ShadowMembers("...")]` attribute names a real type. Its
  defining assembly comes from the type definitions of the shared framework the compiler is pinned to
  (`Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` of `global.json`'s SDK; the same index idea as
  `FrameworkIl`). That part is exact: 743 targets in 243 files, 467 in System.Private.CoreLib, 276 in 28 other assemblies
  (Security.Cryptography 86, Text.Json 48, System.Collections 22, Regex 14, ComponentModel.TypeConverter 12, ...).
- **Lines per target.** The lines from one shadow attribute to the next belong to its target (a `ShadowMembers`
  class with several targets shares them); the header and helpers before the first attribute go to the first target
  (the one file with a large non-shadow preamble, `Core.cs`, is split by hand). 111 files hold no shadow attribute
  (support code of a family): they take the class of their directory or a per-file override in the tool.
  The attribution is approximate at the edges and exact in total.
- **Classes.** (1) CORE-CONTRACT: runtime-coupled, stays; (2) CORELIB-PURE: a System.Private.CoreLib type that is
  plain managed code upstream; (3) FRAMEWORK-ABOVE: shadows a type of another framework assembly; (4) GLUE:
  csharpc-specific (libc/Win32/OpenSSL bindings, compiler hooks); (5) DATA: tables.
- **Verdicts.** `keep`; `shrink` (a part is contract, the rest upstream's); `delete-when-IL-wins` (a ceiling: the
  file goes when the real IL of its types passes the per-library A/B of ADR 0023, with the blockers listed). A
  verdict is not a decision to delete: speed > security > size still decides each case, and the Json and Regex
  rows belong to the A/B in #187/#188/#189.
- **Other columns.** `origin` (the header names dotnet/runtime: `ported`), `data_lines` (literal tables and lines
  over 300 characters), `compiler_hooks` (string literals naming the shadowed type in `CodeGen`/`Frontend`, i.e.
  `Intrinsics.cs`, `BclValueTypes*.cs`), `fan_in` (other corelib files that mention the main target's name),
  `basis` (`read`: opened and checked against the code; `rule`: classified by the rules in the tool).

What the numbers say:

- **85 % of the corelib sits in classes the principle gives to upstream** (CORELIB-PURE and FRAMEWORK-ABOVE), and
  210 of the 354 files already name dotnet/runtime as their source: most of the corelib is a *port* of the code the
  real IL contains. Deleting it is mostly a matter of the IL front-end and the contract, not of semantics.
- **Globalization (38,376 lines) is not data.** Only about 3,400 lines are tables (`IcuLocaleData.cs` is a verbatim
  port of upstream's table, plus the generated Unicode/Bidi/Grapheme tables); the rest is upstream's culture,
  calendar, collation, parsing and formatting code, ported. All DATA files together (adding the Regex tables and the
  Latin1 best-fit table) are 5,374 lines, 3.2 % of the corelib.
- **The contract is small by lines (8.6 %) but not by dependency.** Task, CancellationTokenSource, wait events and
  the async builders are *runtime* objects of the coroutine lowering (docs/10-async.md, `src/runtime/async.c`);
  upstream's Task cannot come as IL without changing the async lowering. Reflection (3.2k lines) sits on compiler
  metadata (ADR 0018). These two are most of the contract.
- **Not every shadow is a port.** `List<T>`, `Dictionary<,>` and `HashSet<T>` are csharpc's own code mirroring
  upstream's behaviour (the header says so), with internals the rest of the corelib touches (`_items`, `_size`,
  the Linq span fast paths, `CollectionsMarshal`) and compiler-coupled helpers (`CoreIntrinsics.AreEqual/HashOf`,
  `LibraryFrames`). `Memory<T>` is laid out without the array/MemoryManager/string object (stated in
  `Buffers/ReadOnlySequence.cs`), which real `System.Memory` IL and every `Memory<byte>` overload would need.
  The header of `Net/Tls.cs` still calls TLS a stub (`Net/SslStream.cs` has grown since), so the Net rows are the least reliable.
- **String, Array and the primitives are member-level.** The type stays ours (layout), but a good part of its members
  (`String.Split/Join/Trim/Pad/Replace`, `Array.Sort/IndexOf/Resize`, `Double.*` generic-math statics,
  `Math.*` that are plain C# upstream) are plain managed code. A mixed mode at type granularity cannot split them;
  `ShadowMembers` already works per member on the compiler side, `IsShadowedIlType` does not.

## What the contract has to stand in for: the framework's runtime entry points

The shared framework's `System.Private.CoreLib` is **CoreCLR's**: its runtime-coupled surface is 200 `InternalCall`
(FCall) methods and 328 QCalls, plus 160 imports of `libSystem.Native` (123) and `libSystem.Globalization.Native`
(37), on **80 types** (`tools/il-first/ownership.sh --contract` lists them). A type that reaches none of those is
plain managed code. The heaviest, by entry points: `Interop+Sys` (122 libSystem.Native imports), `RuntimeTypeHandle`
(16 + 32), `Interop+Globalization` (37), `GC` (13 + 19), `RuntimeMethodHandle` (18 + 11), `RuntimeAssembly` (4 + 23),
`Math`/`MathF` (25 + 25, libm), `MetadataImport`, `Thread` (3 + 15), `RuntimeHelpers` (5 + 11), `String` (10 + 2),
`Marshal`, `Delegate`, `Exception`, `Array`, `Interlocked`, `ValueType`, `SpanHelpers` (2 QCalls). That list is the
size of the thin contract layer the owner describes. The collections, StringBuilder, Convert, number formatting,
Guid and the culture logic are *not* among those types; they reach the list only through `Array`, `String`,
`RuntimeHelpers`, `Unsafe`, `Interlocked` and the default comparers.

Libraries above CoreLib that import natives (so are ineligible for IL until the shim question is decided, ADR 0013):
System.Security.Cryptography (310 OpenSSL + 6), System.Net.Security (114 OpenSSL + 21 + 3), System.Net.Sockets (68),
System.Diagnostics.Process (29), System.Console (24), System.IO.Pipes (17), System.IO.MemoryMappedFiles (15),
System.Net.Primitives (13). **System.Text.Json, System.Text.RegularExpressions, System.Linq and System.Collections
import nothing native.** That is the line between "an IL front-end question" and "a native shim question".

**A question for the owner that this map raises:** csharpc already ports one shim (libSystem.Globalization.Native,
in `src/runtime/globalization`, linked into the program). The same could be done for libSystem.Native (and the
OpenSSL shim) by building upstream's C sources in the runtime build, which would let CoreLib's own IO, Process,
Console, Sockets and Cryptography IL bind to them, and would make `IO/Posix.cs`, `Win32.cs`, `Net/NetNative.cs`,
`Net/SocketEngine.cs` and the Crypto glue (about 2,900 lines of GLUE) deletable; the cost is that the OS boundary
then follows upstream's shim API (and its size) instead of libc directly. Part B does not decide this.

## Verification of the classification

46 files were opened and checked (header and the coupling to the contract: `CoreIntrinsics`, `Unsafe`,
`RuntimeHelpers`, runtime tasks and events, native imports); they carry `basis = read` in the TSV. 22 more headers
(Json, Crypto, Net, Reflection, Tasks, Threading, IO, Globalization) were read while refining the rules. Reading changed the rule-derived result for these, which are fixed in the tool:

- `Core.cs` is not one family (CoreIntrinsics and the throw helpers are GLUE, the default comparers are contract);
- `ArrayExtras.cs` is `shrink`, not `keep` (generic `Array` statics are plain managed code);
- `IcuLocaleData.cs` is a port of upstream's table, not csharpc's own;
- `CancellationToken*`, `ManualResetEventSlim`, `Timer`, `TimeProvider`, `SynchronizationContext` are runtime-backed
  (async.c / threads.c), not plain managed code; `SpinLock`, `ReaderWriterLockSlim`, `SemaphoreSlim`, `Barrier` are
  ports;
- the calendars and `TimeSpanParse` reach the culture cluster (ICU), not only resources;
- `AssemblyName` is not an attribute type; small families inside a large file no longer decide its blockers.

Confidence: **high (exact)** for class FRAMEWORK-ABOVE versus System.Private.CoreLib (metadata) and for the line
totals; **about 85 %** for the CONTRACT/PURE split per file (46 of 354 files read, 7 needed a rule change, none
changed class by more than a family); **medium** for the verdicts of unread files and for every blocker, which are
hypotheses from the code's own headers and from what the CoreCLR CoreLib calls, to be replaced by measurements as
each library goes through the A/B (Part B does this for collections, StringBuilder, number formatting and Guid).

## Part B: the mixed-mode CoreLib spike (issue #191)

Under boundary A of [ADR 0024](adr/0024-runtime-boundary.md) (our C runtime plus the contract layer, upstream above), can a
type of System.Private.CoreLib drop its shadow and compile from the framework's IL while the rest of the corelib stays?
The spike answers it for List, Dictionary, HashSet, StringBuilder, Guid and number formatting, without changing a default.

### Mechanism

- **The slicer** (`tools/il-first/slicer`, Mono.Cecil from the ILLink tasks package the SDK restores) reads the shared
  framework's `System.Private.CoreLib.dll` and cuts, from the root types, the methods they reach (calls, field accesses, type
  tokens, base types, interfaces, the virtual methods of every used type). A type the reference pack declares publicly is a
  *stop type*: references to it stay references to the reference-pack assembly, which csharpc serves from its shadows and
  intrinsics, so the slice binds like any framework IL assembly (ADR 0013). Every other CoreLib type reached joins the slice,
  under `CsharpcCoreLib.Upstream.*` so it never collides with the reference pack's names. What the slice calls on a stop type
  that the reference pack does not declare is the **contract**; the extern methods it reaches (FCalls, QCalls, P/Invokes)
  are counted too (none for these six types).
- **The compiler hook** (`CSHARPC_UPSTREAM_MAP=<slice>.map`, `Frontend/UpstreamSlice.cs`, off by default): the shadows of the
  listed types and their nested types are dropped and the real types map to the slice's, as they map to a shadow. Stack traces
  print the BCL names. Members the reference pack lacks resolve through the corelib's shadows (PR #222, issue #220).
- Reproduce: `tools/il-first/slicer/slice.sh out.dll 'System.Collections.Generic.List!1'`, then
  `tools/il-first/slicer/compare.sh program.cs out.dll` (shadow and slice builds: size, compile CPU, run CPU, output equality).

### What it found

1. **The contract is small, and it is the internals of a handful of types.** List needs one member beyond the public surface;
   Dictionary and HashSet three; StringBuilder sixteen (String 2, CompositeFormat 4, Buffer, ArrayPool, MemoryExtensions,
   ArgumentNullException, Enum, DefaultInterpolatedStringHandler, Rune, the internal `Span<T>` constructors). PR #222 adds the
   ones the six types call (12 members in the corelib) and the mechanism that resolves them. Number formatting is the exception:
   33 members, 19 of them `NumberFormatInfo` internals, i.e. the culture cluster (CultureInfo, CultureData, ICU) comes with it.
2. **Unsupported IL constructs: none of the IL opcodes.** `localloc` (54 sites in Number, 1 to 7 elsewhere) and the
   `ref`-returning accessors lower. What stopped the slices were member resolution (fixed in #222), two missing
   capabilities of the primitives (#221: CoreLib-internal static abstract interfaces such as `IUtfChar<T>`, and interface
   dispatch on built-in types for `ISpanFormattable`/`IFormattable`), and the default comparers (#223).
   #221 is closed by two general mechanisms. The slicer hosts, per built-in type, the methods that implement the static
   abstract members of the slice's interfaces (`implementers`/`internal-interfaces` list them: `IUtfChar<T>` on char and byte,
   `IBinaryIntegerParseAndFormatInfo<T>` on the 11 integers and char, `IBinaryFloatParseAndFormatInfo<T>` on float, double,
   Half, BFloat16) in a `<Type>InterfaceMembers` class named in the map file (`members:System.Char=...`); the constrained-call
   resolution (`FunctionCodeGen.BuiltinInterfaceMembers.cs`) looks a member up there, and a member with no implementation is
   an explicit CSLLVM0001 naming the interface member and the constraint type, no longer invalid IR. Boxed built-in values
   dispatch `ISpanFormattable.TryFormat` / `IUtf8SpanFormattable.TryFormat` through the corelib's `BoxedSpanFormattable`, as
   `IConvertible` goes through `BoxedConvertible`. Guid, StringBuilder (all 4 samples) and System.Number now compile from
   their slices; `tests/slicer.sh` runs the samples against them.
3. **Default comparers decide Dictionary and HashSet.** Upstream calls `EqualityComparer<TKey>.Default` per probe, which the
   shadows replace by inline `CoreIntrinsics.AreEqual/HashOf`: +40 to 50 % run time and the larger code. Until the IL front-end
   lowers the default-comparer calls like the shadows do (#223), a Dictionary or HashSet flip fails the speed rule.
   #223 lowers them so (`FunctionCodeGen.DefaultComparers.cs`): `EqualityComparer<T>.Default.Equals/GetHashCode` and
   `Comparer<T>.Default.Compare` on a closed T are the same inline code as `CoreIntrinsics.AreEqual/HashOf/Compare`, in the IL and
   the source front-end, and the getter call that made the comparer is erased when nothing else uses it. Two other costs the
   framework's collections showed came out with it: `typeof(T).IsValueType` kept a dead `csrt_type_from_mt` call (the Type
   object is now erased when unused, which is most of Dictionary's remaining gap), and `x.GetHashCode()` on a value-type `T`
   (HashSet) boxed and dispatched virtually (now `HashOf`). Callgrind instruction counts, same program, -O2, shadow / slice before
   / slice after: Dictionary<int,int> insert 146.4 M / 211.3 M / 151.3 M, lookup 97.4 M / 138.1 M / 93.3 M, remove 167.6 M / 275.8 M
   / 171.0 M (within 5 %); HashSet<int> add and contains 73.2 M / n/a / 74.6 M; Dictionary<string,int> +21 % and HashSet<string> +31 %
   remain (the string-comparer family, out of scope of #223). The slice's binary stays about 50 % larger.
4. **`SR` is a size decision.** The CoreLib resource strings behind the exception messages (1 459 entries) cost 22 KB of
   strings plus the ResourceManager and culture code if embedded: List went from +132 KB to +12 KB by letting each reached
   `SR` getter carry its text as a literal (the slicer does what ILLink's resource substitution does). A real flip needs that
   step in the IL front-end, not a slicer.
5. **Reflection-based generic instantiation is the other hard dependency.** `List<T>.Sort` reaches
   `ArraySortHelper<T>.CreateArraySortHelper`, which creates its helper with
   `RuntimeTypeHandle.CreateInstanceForAnotherGenericParameter`; the spike redirects the helper to a corelib type (a copy of the
   span) and #224 asks for the compile-time intrinsic NativeAOT has.
   #224 adds it (`FunctionCodeGen.IlGenericInstantiation.cs`): a call with `typeof` constants becomes `newobj G<T>::.ctor()`,
   anything else is an explicit diagnostic, and `System.RuntimeType` in framework IL means `System.Type`. Measured first: the
   `ArraySortHelper<T>` call sits behind `RuntimeFeature.IsDynamicCodeCompiled`, which csharpc folds to false as NativeAOT does, so
   `List<T>.Sort` and `Array.Sort` compile from the framework's own helper without the redirect (removed from the slicer, sample 1299)
   and never reach the intrinsic. The unguarded callers are `ComparerHelpers.CreateDefaultComparer` / `CreateDefaultEqualityComparer`
   (the real `EqualityComparer<T>.Default` and `Comparer<T>.Default`); they stop one step earlier, at
   `typeof(IEquatable<>).MakeGenericType(type)` ("csharpc compiles only the generic instantiations the program creates"), which is
   what a flip of the default comparers needs next. The intrinsic itself is tested with an IL library written with Cecil
   (`tests/slicer.sh`, `tools/il-first/slicer/Synth.cs`) because no C# program can call the internal member.
6. **Deleting a shadow can mean deleting compiler hooks.** StringBuilder's interpolation handler and
   `DefaultInterpolatedStringHandler` are represented by the shadow `StringBuilder` in `TypeMapper` and
   `FunctionCodeGen.Tuples.cs`/`Calls.cs` (about 120 lines); with the real struct those paths must go, and they produced
   silent empty output when left in place (`sb.Append($"...")` appended nothing): the spike disables them when the slice serves
   StringBuilder.
7. **Other code leans on the shadows' layout.** Only `LinqSpans.cs` (the `List<T>` span fast path, through
   `CoreIntrinsics.IsExactClass<ListImpl<T>>`) and `CollectionsMarshal` (in `List.cs`) name `ListImpl`; the Linq fast path
   silently falls back to the slow path once List is the real class, and `CollectionsMarshal.AsSpan(list)` must come from
   the IL too (root it with List) when a program uses it.

### Proposed boundary, and the order

The numbers support boundary A for collections and text, with the contract growing by the internals listed above (12 members so
far, plus the spike's own shims) and no change to the runtime. Order: **List** first (go; flip PR deletes `ListImpl`, its enumerator object and the Linq
hook), then the primitives' interface work (#221) and the default comparers (#223) which unblock **HashSet**, **StringBuilder**,
**Dictionary**, **Guid**, then number formatting together with the culture cluster. Per #187's rule each flip PR deletes its
shadow and reports the lines removed; none is part of this spike. If the owner would rather not keep the contract members in the
corelib, the alternative is member-level mixed mode for String and Array (their internals are the bulk of the contract), which
`IsShadowedIlType` does not support yet.
