# ADR 0022 — TLS and X.509: the corelib over OpenSSL, not the framework's IL

- **Status:** Accepted (2026-11-06). Implemented: X.509 certificates and chains (step 1), `SslStream` client and server and
  `https://` through `HttpClient` (step 2), on Linux; the same code on macOS arm64 over Homebrew's OpenSSL 3 and on Windows
  x64 over the OpenSSL 3 DLLs (addenda, 2026-11-07).

## Context

`HttpClient` works over plain HTTP/1.1 ([ADR 0013](0013-framework-il.md), "Mixed assemblies"); `https://`, `SslStream`
and the certificate types were explicit `NotSupportedException`s. NativeAOT parity (ADR 0016) needs TLS: Kestrel's
HTTPS, `HttpClient` to real servers, `SslStream` itself. .NET's own stack on Linux is
`System.Net.Security` (the `SslStream` state machine, `Interop.OpenSsl`) over `System.Security.Cryptography`
(X509Certificate2, chains, PKCS#12, keys), whose native half is `libSystem.Security.Cryptography.Native.OpenSsl`, a
shim over libssl/libcrypto that the shared framework ships and the NativeAOT runtime pack ships as a static archive.

## Options measured

1. **Framework IL, like System.IO.Compression or System.Net.Http** (the route the other framework libraries took).
   `--framework-il System.Security.Cryptography` and `System.Net.Security` both stop at the first gate:
   "it calls native code of the .NET runtime (libSystem.Native)". These assemblies call the whole `libSystem.Native`
   (file reads for the certificate stores, environment, `SystemNative_*` helpers), which carries .NET's signal handling
   and child-process machinery and which `NativeAotPack` deliberately lets only System.Formats.Tar and ZipFile call
   (it would compete with csharpc's runtime). Past that gate the work is large and open-ended:
   - `System.Security.Cryptography` holds types the corelib already implements as shadows (`RSA`, `Aes`,
     `SymmetricAlgorithm`, `HashAlgorithmName`, `RandomNumberGenerator`, the hash classes, `CryptoStream`). The IL
     `RSAOpenSsl`/`X509Certificate2` code derives from and calls members of those (`ImportPkcs8PrivateKey`, ...) that
     the shadows lack, so it needs either a complete second RSA/hash surface or removing the shadows, which moves every
     existing crypto sample onto the shim and onto IL.
   - The shim's static archive links, but its callers marshal `SafeHandle`s through `LibraryImport` stubs
     (`SafeHandleMarshaller<T>`: one of the open blockers of docs/18-compatibility.md), pass delegates as native
     callbacks (ALPN selection, verification, client-certificate and SNI callbacks) and rely on `ArrayPool`, `ValueTask`
     state machines and `Memory<byte>` pinning in `SslStream`'s I/O (about 4 000 lines, `SslStream.IO.cs`/`.Protocol.cs`).
   - A program using `SslStream` would link System.Security.Cryptography's lowering closure (certificate stores, PKCS#7,
     CMS-adjacent code), the way Regex links its engine: hundreds of KB, minutes at `-O2`.
   - It would still need a port for macOS (Security.framework shim) and Windows (the same assemblies, but SChannel
     P/Invokes and `SafeHandle`s), neither reachable from the framework IL without those same blockers.
2. **The corelib over OpenSSL directly** (what `Crypto/Rsa.cs` and `Crypto/AesNative.cs` already do for RSA and AES):
   `X509Certificate`/`X509Certificate2`, `X509Chain`, the collections and the loaders are written in C# in the corelib,
   reading DER themselves (the fields the API reports) and calling libcrypto for what needs it (PKCS#12 and PEM
   decoding, private keys, chain verification); `SslStream` follows over libssl with memory BIOs. libcrypto/libssl are
   opened on first use (`DllImport("libssl.so.3")`), the same dependency every .NET Linux app has, so programs that
   don't use TLS don't load them and nothing is linked statically.

## Decision

**Option 2.** The shadow classes keep .NET's public surface and exception types and messages, copy .NET's managed
logic where it is portable (`X509Certificate.ToString(true)`, thumbprints, name formatting after
`X500NameEncoder`, the chain status mapping after `OpenSslX509ChainProcessor`) and call OpenSSL 3 for the
cryptographic work, like the shim does. What isn't implemented is an explicit diagnostic (a compile-time
CSLLVM0002 where the member is absent from the shadow, a `NotSupportedException` naming the feature where it can't
be): certificate extensions (`X509Certificate2.Extensions` and the typed extension classes), stores, PKCS#7,
exporting a PFX, `GetNameInfo` for names without CN/OU/O, revocation checking, ECDSA/DSA key getters.

Why not both: with the shadows in place the framework-IL route is closed by construction (a type csharpc implements
makes its assembly ineligible, ADR 0013), and the shadows are cheaper, smaller and let LLVM see through the
wrappers. When a future port of the framework's own stack becomes possible (libSystem.Native admitted for these
assemblies, `SafeHandleMarshaller`), the corelib shadows can be removed type by type; the samples are the oracle
(recorded from .NET) for that switch.

## SslStream

`SslStream` and `AuthenticatedStream` are corelib shadows (`corelib/Net/SslStream.cs`) over libssl 3 with a memory-BIO pair:
the handshake and the data path move TLS records between the BIOs and the inner stream, synchronously or asynchronously
(one code path, `sync` selects `Stream.Read` or `ReadAsync`). The certificate validation runs inside libssl's certificate-verify
callback (`SSL_CTX_set_cert_verify_callback`, an `[UnmanagedCallersOnly]` function that finds its stream through the `SSL*`),
as .NET's `CertValidationInCallback` does on Linux: a rejected certificate aborts the handshake before the client's Finished,
the alert goes out, and the peer sees `SSL_ERROR_SSL`. The validation logic is a copy of `VerifyRemoteCertificateCore`
(policy errors, name check through `X509_check_host`/`X509_check_ip`, chain policy and extra store from the peer's chain, the
callback or the default decision) and so are the exception types and messages, which the samples compare with .NET's. The handshake reads whole TLS
records and applies .NET's frame check ("Cannot determine the frame size or a corrupted frame was received.") before libssl
sees a byte. ALPN (client list, server selection through `SSL_select_next_proto`), TLS 1.2 / 1.3 selection, client certificates,
mutual authentication, SNI (`TargetHostName` on the server), `ShutdownAsync` and the close-notify end of stream are covered.

Not implemented, explicit diagnostics (a `NotSupportedException` naming the feature): `ServerCertificateSelectionCallback`,
`ServerOptionsSelectionCallback` / `SslClientHelloInfo`, `LocalCertificateSelectionCallback`, `CipherSuitesPolicy`,
`SslStreamCertificateContext`, `NegotiateClientCertificateAsync`, channel bindings (`TransportContext.GetChannelBinding`),
`CipherAlgorithm` / `HashAlgorithm` / `KeyExchangeAlgorithm` and their strengths (`NegotiatedCipherSuite` works).

Known difference: .NET resumes the TLS sessions of clients without a validation callback (its `SslSessionsCache`), and a
resumed session skips libssl's verify callback, so a certificate rejected on a later connection to the same host fails after
the handshake with the bare validation `AuthenticationException` instead of the one wrapped in "Authentication failed, see
inner exception."; csharpc never resumes client sessions (the server side can, through libssl's own cache). The samples
order their failing connections first for that reason.

## Platforms

Linux (glibc, x86-64 and arm64), macOS arm64 and Windows x64 (addenda below). WASI (no sockets) keeps the previous
explicit `NotSupportedException` ("TLS and X.509 certificates ... are not supported by csharpc yet"); `https://` keeps
failing with that diagnostic there. Each sample is listed in `tests/platform-skips.txt` as a known gap for WASI.

## Addendum (2026-11-07): macOS arm64 over OpenSSL 3

.NET on macOS uses Security.framework (SecKey/SecCertificate/SecTrust for certificates and chains, SecureTransport's
`SSLContext` for `SslStream`). Options for csharpc:

1. **Security.framework through `[DllImport]`** (CoreFoundation `CFData`/`CFArray`/`CFDictionary` marshalling,
   `SecPKCS12Import`, which needs a keychain for the private key, `SecTrustEvaluate`, `SSLCreateContext` with
   read/write callbacks). Zero dependencies and the system trust store, but it is a second implementation of
   `X509Certificate2`, `X509Chain`, `RSA` and the whole `SslStream` state machine, SecureTransport (deprecated since
   macOS 10.15) has no TLS 1.3, and none of it can be debugged locally: every iteration is a CI round trip.
2. **Network.framework**: block- and queue-based (`nw_connection`), owns the socket; it cannot sit on a managed `Stream`
   as `SslStream` must. Rejected.
3. **The existing OpenSSL 3 code, bound to Homebrew's `openssl@3`** (chosen). The corelib's X.509, chain, RSA and
   `SslStream` code is identical on Linux and macOS; only the library path differs
   (`/opt/homebrew/opt/openssl@3/lib/libcrypto.3.dylib`, `libssl.3.dylib`, in `Ossl.Crypto`/`Ossl.Ssl`; Apple silicon's
   Homebrew prefix is fixed, and an absolute path makes a missing library a `DllNotFoundException` naming it). The
   corelib guard is `CSHARPC_OPENSSL` (defined for Linux, macOS and Windows targets by the driver), replacing
   `CSHARPC_TARGET_LINUX` on the TLS code. The samples 1100-1103 and 553 are the oracle, run on `macos-arm64` CI.

Cost. Binary size: nothing for programs that use no certificate, TLS or RSA type (the bindings are reached only from those
classes, nothing is linked statically and the dylibs are opened on first use, so the macOS size budgets are untouched);
a program that uses them carries what it carries on Linux (measured on Linux x86-64, stripped: X.509 loading, about
0.8 MB; `HttpClient` with `https://` and an `SslStream` server, about 3.9 MB). Run-time: macOS programs that use these types need
`brew install openssl@3` on the machine, the way Linux programs need `libssl.so.3`; `RSA.Create()` joins them, because a
certificate's private key and an RSA key are the same `EVP_PKEY`. The hardening posture is that of the Linux build.

What differs from .NET on macOS, and stays so until the Security.framework follow-up:

- **Trust.** The default chain root set is OpenSSL's (`SSL_CERT_FILE`/`SSL_CERT_DIR`, Homebrew's `cert.pem`) plus the bundle
  macOS keeps at `/etc/ssl/cert.pem`, not the keychain: roots or distrust settings added in Keychain Access are not seen.
  `X509Store` stays out of scope.
- **Protocols.** TLS 1.3 works (OpenSSL), where .NET's SecureTransport stops at TLS 1.2 (the live run of sample 1101 shows
  `SslProtocols.Tls13` failing under .NET on macOS): a deliberate superset, so the sample skips that case on macOS.
  Likewise `RSA` (sample 553): .NET's SecKey-based RSA reports other legal key sizes, refuses keys under 1024 bits and
  doesn't throw `ObjectDisposedException` from `ExportParameters`; csharpc keeps the OpenSSL behaviour of Linux there.
- **Messages that follow .NET's macOS backend** (compared by the live samples): a failed certificate validation is thrown as
  the `AuthenticationException` itself, not wrapped in "Authentication failed, see inner exception." as on Linux (.NET
  validates after SecureTransport's handshake); chain status texts for an untrusted root and an expired certificate are
  Security.framework's ("The certificate was not trusted.", "An expired certificate was detected."), other statuses keep
  OpenSSL's text; unreadable certificate data is "Unknown format in import."; a missing certificate file is the file
  system's exception; a protocol version mismatch has "bad protocol version" as inner exception message.
- Everything the Linux list above names as not implemented (callbacks that select the certificate, `CipherSuitesPolicy`,
  `SslStreamCertificateContext`, revocation, PKCS#7, extensions, stores) keeps its explicit "not supported by csharpc yet"
  diagnostic on macOS too.

The zero-dependency route (option 1) remains the follow-up: it would replace `Ossl` per type behind the same shadows,
with the samples as the oracle, and make the OpenSSL path optional on macOS.

## Addendum: Windows over OpenSSL (2026-11-07, issue #134)

.NET's Windows stack is CNG/CryptoAPI for keys and certificates and SChannel (SSPI) for `SslStream`. Two ways to get
`SslStream`, `X509Certificate2`, `X509Chain` and `https://` there:

1. **SChannel and crypt32** (what .NET does): no extra DLL, but a second implementation of everything this ADR built:
   the SSPI record loop (`InitializeSecurityContext`/`AcceptSecurityContext`/`EncryptMessage`/`DecryptMessage` over
   buffer descriptors), `PFXImportCertStore` and `CertGetCertificateChain` behind a different certificate model, a second
   mapping of chain status and policy errors, and no way to debug it except on a Windows machine (CI iterations of ten
   minutes).
2. **The same corelib code over OpenSSL 3 for Windows** (chosen): `OpenSsl.cs` binds `libcrypto-3-x64.dll` and
   `libssl-3-x64.dll` (the names of the official and MSYS2 builds) on Windows, loaded on first use from the executable's
   directory or `PATH`; `SslStream`, `X509*` and `RSA` are unchanged (a `CSHARPC_OPENSSL` define, set for Linux and
   Windows targets, replaces the `CSHARPC_TARGET_LINUX` guards). The Linux samples, recorded from .NET, are the oracle
   and run unchanged, and the stack can be exercised under Wine with the DLLs next to the executable.

What the choice costs:

- **A run-time dependency**: unlike Linux, where libssl.so.3 is a system library, Windows doesn't ship OpenSSL. A program
  that uses certificates, `SslStream`, `https://` or `RSA.Create()` must ship the two DLLs (OpenSSL 3.x, x64) next to its
  executable or have them on `PATH`; without them the first use throws `DllNotFoundException: Unable to load DLL
  'libssl-3-x64.dll' ...`, the diagnostic of any P/Invoke. Programs that use none of it load nothing and are
  byte-identical in size. CI downloads MSYS2's OpenSSL 3.6 package (pinned release and checksum, `setup-toolchain`) and puts
  the two DLLs on `PATH`.
- **Windows `long` is 32 bits**: the bindings that mirror C's `long`/`unsigned long` (`d2i_*` lengths, the `SSL_ctrl`
  family, `ERR_get_error`) use `OsslLong`/`OsslULong`, 32-bit on Windows and 64-bit elsewhere.
- **Trust**: OpenSSL has no system store on Windows, so `X509ChainTrustMode.System` loads the `ROOT` certificate stores of
  the current user and the local machine (`CertOpenStore`/`CertEnumCertificatesInStore`, read once) as trust anchors.
  Not consulted: roots Windows would download on demand (the AuthRoot program), the `CA` intermediate store (servers send
  their intermediates), certificate revocation. `X509Store` stays an explicit diagnostic.
- **RSA**: `RSA.Create()` uses the same OpenSSL on Windows (it was a CNG known gap); CNG can replace it later, for
  programs that use RSA without TLS, without touching the TLS code.
- **Observable differences from SChannel**, found by comparing with .NET on a Windows runner: a rejected certificate is
  thrown as the validation failure itself (csharpc matches that on Windows, where OpenSSL's callback wraps it on Linux);
  servers send no TLS 1.3 session tickets on Windows (a client that closes without reading them makes Windows reset the
  connection and discard the server's unread close_notify); the inner exception text of a failed handshake is the library's
  own, how many server handshakes complete before a client rejects the certificate is the stack's, and a peer that leaves
  unread data ends a read as EOF or a reset. The TLS samples print only what .NET defines and normalize these.
- **Texts from the TLS library**: error messages that come from OpenSSL (`error:...`) differ from SChannel's where .NET
  reports the OS's, as on Linux; a sample that prints them is a `live:` entry on Windows if .NET's output differs.

SChannel remains the zero-dependency follow-up: it can be added behind the same `SslStream` shadow as a second backend
(an SSPI-based stream plus a CNG-backed certificate type) when shipping OpenSSL is not acceptable.

## Consequences

- `System.Collections.CollectionBase` became a shadow (`corelib/CollectionBase.cs`, a port): `X509CertificateCollection`
  derives from it as in .NET. System.Collections.NonGeneric is a *mixed* assembly now (ADR 0013): its SortedList, Queue
  and Stack, which `CookieContainer` uses, still come from IL.
- Programs that use no certificate or TLS type are byte-identical in size and speed: the OpenSSL bindings are only
  reached from the new classes.
- The OpenSSL library is a run-time dependency of programs that use these types (libssl.so.3 / libcrypto.so.3, OpenSSL 3).
  A machine without it gets the `DllNotFoundException` of any P/Invoke, where .NET would fail with its own message.
- `https://` works through `SocketsHttpHandler` unchanged (its IL calls `SslStream.AuthenticateAsClientAsync(options)`);
  programs that don't use TLS don't link any of it.
- The certificate's private key stays an OpenSSL `EVP_PKEY` (`GetRSAPrivateKey()` shares it), so SslStream hands it to
  libssl without re-importing.

## Addendum: Windows without OpenSSL, a spike (2026-11-08, issue #143)

Question: can Windows drop the OpenSSL DLLs by compiling .NET's own `System.Net.Security` (SSPI/SChannel) and
`System.Security.Cryptography` (CNG, crypt32) from the shared framework's IL, as ADR 0013 did for the compression and
HTTP libraries? The framework's Windows build of those assemblies P/Invokes `sspicli`, `bcrypt`, `ncrypt` and `crypt32`
directly (no native shim of its own), so nothing has to be linked besides the OS DLLs, which the bindings load on
first use like any `[DllImport]`.

**The opt-in switch.** `CSHARPC_WINDOWS_NATIVE_TLS=1` (Windows targets only, never the default, no effect on any other
program) does two things: the corelib is built without `CSHARPC_OPENSSL` and with `CSHARPC_NATIVE_TLS`, and
`Frontend/NativeTls.cs` removes the shadows of the OpenSSL-backed family (`X509Certificates.*`, `Oid*`, `AsnEncodedData`,
`RSA*`, `Asymmetric*`, `Cng*`/`Csp*`, `ECDsa`/`DSA` factories, `SslStream`, `AuthenticatedStream`, `Ssl*` options and
contexts, `PbeParameters`) from the shadow index and from the "types csharpc implements" set that decides eligibility.
`System.Security.Cryptography` and `System.Net.Security` become *mixed* assemblies (ADR 0013): the hash, HMAC, AES,
`CryptoStream`, random and Negotiate shadows stay, everything else is IL. The framework directory must be the Windows
one (on a Windows host it is; a cross compile from Linux points `CSHARPC_SHARED_FRAMEWORK` at
`Microsoft.NETCore.App.Runtime.win-x64/runtimes/win-x64/lib/net11.0`, because the Linux shared framework holds the
Linux build of these assemblies, with `Interop.OpenSsl` in place of `Interop.BCrypt`).

**What blocked it.** Compiling samples 1100, 553, 1101, 1102, 1103 and 1231 for `x86_64-w64-windows-gnu` against the
Windows IL (the lowering stops a method at its first unsupported construct, so the list is the reachable closure; an
`--il-survey` over all three assemblies, 11 427 IL methods, adds only the rows marked *survey*):

Eleven distinct constructs, all fixed (sample `1250_bcl_framework_crypto_surface` records them from real .NET and runs
on every platform); after them all six samples compile for Windows with no diagnostic, and the executables link without
a single unresolved symbol (the OS DLLs are bound on first use). **None of SafeHandle marshalling, the SSPI structs
(`SecBufferDesc`, `SecHandle`), the CNG key blobs or the function-pointer P/Invokes was a blocker**: the
`LibraryImport`-generated stubs are plain IL over `DllImport`s, which the front-end already lowers.

**Cost, measured** (cross compile on Linux x86-64 for `x86_64-w64-windows-gnu`, `-O2`, stripped, CPU seconds on a shared
machine, so wall clock is not comparable):

| Program | OpenSSL path | Native route |
|---|---|---|
| 1100 (load PKCS#12/PEM/DER, chains) | 737 KB; lower 10.5 s, optimize 53 s, codegen 29 s | 2 063 KB (2.8x); lower 35.6 s, optimize 72 s, codegen 61 s; 2 764 IL + 4 224 corelib methods against 0 + 2 269 |
| 1103 (HttpClient over https, SslStream server) | 3 363 KB; lower 38 s, optimize + codegen 220 s | 5 024 KB (+49 %); lower 47 s, optimize + codegen 299 s (+35 %); 5 241 IL + 8 377 corelib methods against 2 871 + 6 866 |

Programs that use no TLS, X.509 or RSA type are unaffected on either path. The native route is bigger and slower to
compile because the OpenSSL path wraps one C library in a few thousand lines of corelib, where the native one compiles
.NET's whole managed stack over the OS (the SChannel record loop, the certificate model, PKCS#12/PKCS#7/CMS parsing).

**Runtime evidence.** Wine 10 runs the 1100 executable far enough to print the subject, issuer, serial, thumbprints
and hash of the PFX certificate exactly as the sample expects (the PKCS#12 import ran through .NET's own `CertificatePal`
over crypt32/ncrypt), then stops at `SystemTimeToTzSpecificLocalTimeEx`, which Wine 10 lacks; 553 generates an RSA key
through `RSACng`, exports its parameters and makes and verifies a PSS signature, then stops in Wine's GnuTLS-backed
PKCS#1 encryption. Neither is csharpc's. The real answer for SChannel needs a Windows runner (CI results below).

**Recommendation: go, as the Windows end state, behind the switch until the Windows runs are green.** The feared
blocker, a large unsupported-construct surface in the SSPI/CNG interop, did not exist: the whole closure needed eleven
small, general BCL fixes. The costs are size (about +1.7 MB for an https client) and compile time (about +35 %), which
the OpenSSL path does not pay; against that stand no run-time dependency, security fixes through the OS, SChannel's
exact exception texts (the `live:` Windows entries stop being approximations) and deleting the Windows half of the
OpenSSL surface. OpenSSL remains the Windows default until the native route passes the Windows CI on 553, 1100-1103
and 1231 and its size is within a budget the owner accepts; the size is the open question, since a size regression is
a bug (AGENTS.md) and this one is the price of compiling the framework instead of a C library.
